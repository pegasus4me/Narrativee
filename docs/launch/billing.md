# Trial and subscription billing rollout

The backend owns balances. One credit is 10,000 integer microdollars ($0.01). Accounts receive 80 total trial credits for 168 hours; Starter receives 500 credits per monthly period and Pro receives 1,500. Annual billing still creates monthly buckets. Credits do not roll over. A provider call first reserves its conservative maximum; completed usage reduces that reservation to actual spend. Deductions finalize when the parent operation has saved a result. Failed operations release reservations and record known provider costs as Narrativee overhead. Delivery markers are saved in the same transaction as research results, conversations and server canvas saves. Recovery uses the original bucket, including after it expires.

## Configuration before launch

Keep `BILLING_ENABLED=false` until the following are complete:

1. Apply application migrations, including `0021_billing.sql`, to a staging database. Use `pnpm --filter backend db:migrate-brands`. Billing tables must be accessed through the server database role, which owns the tables or bypasses RLS; browser/Data API roles have no access.
2. Verify every configured model against [OpenAI provider pricing](https://developers.openai.com/api/docs/pricing). The bundled catalog verifies standard short-context `gpt-6-luna`, `gpt-6.1-sol` and `gpt-6-astra`, with conservative 32,000 input and 8,000 output token caps. Existing defaults `gpt-5.6-luna` and `gpt-image-2` are deliberately unavailable until verified entries are configured; no historical or batch prices are substituted. Set `OPENAI_MODEL`, `BRAND_IDENTITY_MODEL`, `BRAND_BOARD_TEXT_MODEL` and `BRAND_BOARD_IMAGE_MODEL` intentionally.
3. Configure `AI_MODEL_RATES_JSON` for other models. Each entry contains `version`, official provider `source`, ISO `verifiedAt`, `kind`, `input`, `cachedInput`, `cacheWrite`, `output`, `maxInputTokens` and `maxOutputTokens`. Rates are USD per million tokens. Image entries need verified image input rates and a maximum output token bound for a single high-quality 1024×1024 image; reliable returned text/image token breakdown is mandatory. Cached image usage without an explicit breakdown is unavailable. Built-in web search additionally needs a verified `contextWindowTokens` bound and `longContext` rates with a token `threshold`; its call fee is $0.01. Unsupported tools and opaque provider contexts are unavailable.
4. Firecrawl homepage scraping and discovery searches within the initial onboarding scan do not consume Narrativee credits and are covered as operating overhead; AI analysis, follow-up competitor research and later scrapes remain metered. Configure `AI_TOOL_RATES_JSON` with `firecrawl:scrapeHomepage` and `firecrawl:searchWeb`. Each fixed-request contract contains `microdollars`, `version`, `source` and ISO `verifiedAt`. Verify costs against the account's actual provider terms, including screenshot/branding formats and at most eight search results. Failed tool responses with uncertain charges are overhead. Jev reviewer costs, which have no reliable usage report, remain overhead.
5. Use a **Stripe test secret key** and run `pnpm --filter backend billing:setup-test`. This prepares two products, four prices and a portal configuration. It refuses live credentials. It writes price/portal IDs to ignored `apps/backend/.env.billing.test`; copy these settings to the staging environment. Prices must be USD 1900/month, 18240/year, 4900/month and 47040/year. Checkout uses approved IDs from the backend. No Stripe trial is configured.
6. Configure `STRIPE_WEBHOOK_SECRET`, `STRIPE_PORTAL_CONFIGURATION_ID` and `WEB_APP_URL`. The portal must allow invoices, payment-method updates and cancellation at period end, with subscription updates disabled. Downgrades and interval changes are deferred. Set the webhook API version to match the installed Stripe SDK (recorded in its `cjs/apiVersion.js`). Register `POST /api/billing/webhook` before all JSON parsers, with its raw request body intact. Subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `invoice.finalization_failed`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.updated` and `charge.dispute.closed`.
7. Complete the real Stripe test-mode cases below, then record ISO `BILLING_TEST_VERIFIED_AT`. Run representative AI operations with each configured model and compare provider usage/cost against stored rate snapshots, then record `AI_COST_CHECKS_VERIFIED_AT`. These dates are attestations to completed checks, not a replacement for the checks.
8. Run `pnpm --filter backend billing:verify`. Startup refuses `BILLING_ENABLED=true` if rates, required credentials, verification attestations, approved prices or the portal policy are missing. Verify the production environment separately before enabling it.

## Automated checks

`pnpm --filter backend test:billing` creates a new local `billing_test_*` database, runs mocked provider and Stripe tests, and drops only that disposable database. It refuses remote database hosts. From `apps/backend`, run `node --import tsx scripts/run-billing-tests.ts trial` for real Better Auth signup/session and HTTP access tests in a separate disposable `trial_flow_test_*` database. Neither suite makes paid provider or Stripe network requests.

The billing suite checks microdollar accounting, cached usage, nested operations, retry deduplication, concurrent reservations, failure refunds, stream terminal usage, one-time legacy enrollment, durable delivery markers, abandoned work, expiry boundaries, month-end anchors, annual monthly allowances, signature verification, forged redirects, confirmed invoice grants, webhook duplicates/order, Starter-to-Pro upgrades, failed payments and refunds. Typecheck/build both applications. The upgrade dialog was visually checked at desktop and 390px mobile widths, with monthly/yearly switching and dismissal; public pricing preserves plan/interval through signup.

## Stripe test-mode acceptance

Run a real hosted checkout for both plans and both intervals. Test cancellation and delayed webhooks: the redirect must not grant access. Replay and reorder actual signed events. Create an initial payment requiring authentication, then finish it through its hosted invoice. Submit concurrent/repeated checkouts; only one open session or subscription may exist. Upgrade Starter to Pro with successful and failed prorated payments: the current allowance rises by 1,000 credits only after payment, while usage and the original reset date remain intact. Use a Stripe test clock for annual monthly resets, failed renewals and end-of-term cancellation. Test refunds and disputes for old and current invoices. Any refund invalidates the affected paid period; a won dispute restores eligibility only for the original period, with spent credits retained. Saved work remains readable/exportable in every blocked state.

Test popup behavior on expired-trial entry, while the tab remains open through the deadline, and after an insufficient-credit response, including one wrapped by the OpenAI SDK. Check dismissal, Starter upgrade, Pro reset/contact, project return navigation, unsent drafts and payment confirmation polling. Sign-in/signup and saved work do not require an active paid allowance. Restoring payment access requires a confirmed paid invoice, not a browser query parameter.

## Production cutover

After test-mode acceptance and cost checks, configure the production products/prices and webhook, verify the production configuration, then apply the migration. Deploy the complete backend and frontend together. Run `pnpm --filter backend billing:grant-legacy` once at cutover: only accounts with a null trial deadline receive 80 credits and a fresh seven-day deadline. Replays enroll zero already-enrolled accounts and never reset balances or deadlines. Do not run the production grant during development.

Enable billing only after verification. Keep workers running: once per minute they recover operations whose heartbeat is more than ten minutes old and retry persisted webhook failures. Webhook reconciliation reads current Stripe state under a customer lock; processed event IDs, invoice grants and monthly bucket IDs are unique. Network responses with no reliable usage are never estimated as customer charges. Check unknown-usage records against provider invoices during reconciliation.

## Monitoring

Run `node --import tsx scripts/billing-metrics.ts` from `apps/backend` against the intended database. It returns aggregate provider spend, deductions, absorbed spend, unknown usage counts, reserved funds, stale operations and pending/failed webhooks without customer data. Alert on stale operations, repeated webhook failures, reservation bound violations and unexplained provider-cost differences. Rate snapshots are stored per call, so price changes must publish a new catalog version rather than rewriting past costs. The backend logs recovery/webhook failures and rejects calls whose measured cost exceeds their reservation.
